# Decision log

Short records of choices that shape MoMaTo. "Confirmed" means the product owner decided; "Assumed"
means a reasonable default that is easy to revisit. Once building has started, change an entry by
adding a new one that supersedes it. Don't silently reverse a *Confirmed* decision; ask.

The first review (2026-10-10) confirmed or reworked every entry below before any code existed, so
they were edited in place.

| ID | Decision | Status |
|---|---|---|
| D-001 | The product, the Python package and the settings are called **MoMaTo** / `momato` / `MOMATO_*`; the design's name *Kite* is not used (the wordmark reads "momato"). | Confirmed, 2026-10-10 |
| D-002 | **Stack and conventions follow TaskBoard**: FastAPI + sync SQLAlchemy 2 + Alembic, SQLite first and MS SQL ready; a JSON API with a static Preact/htm frontend without a build step; light/dark theme; TaskBoard's layers, quality gate and documentation layout. The design README's suggestion (React + TypeScript) is not followed. | Confirmed, 2026-10-10 |
| D-003 | Runtime libraries in `[project.dependencies]`, **test and tooling packages in the `dev` dependency group**, the MS SQL driver in the optional extra `mssql`. | Confirmed, 2026-10-10 |
| D-004 | **Accounts, rights and SSO are ported from TaskBoard**: local accounts, roles scoped to org-tree branches, Microsoft Entra ID (OIDC), Windows sign-in and a trusted proxy header as opt-in configuration; TaskBoard's two deployments (corporate Windows server, Linux demo). The code is copied and adapted (D-012), not shared as a library. | Confirmed, 2026-10-10 |
| D-005 | **Seeing other people's booked hours is the permission `hours.view`**, scoped to org branches like any right. By default every signed-in user holds it on their own department; others (department heads) are given it on wider branches or globally through ordinary assignments. | Confirmed, 2026-10-10 |
| D-006 | **Departments are org nodes flagged by administrators**; a person's department is the nearest flagged node on the path from their node up to the root. | Confirmed, 2026-10-10 |
| D-007 | **"Submit week" is a soft marker**, as in the prototype: no lock, no approval; changing hours of a submitted week reopens it. | Confirmed, 2026-10-10 |
| D-008 | **Task progress is entered by hand** (0–100 %); the status is derived (Done at 100 %, Running once started or above 0 %, else Planned); "slipped" when the revised end is later than the planned end. | Confirmed, 2026-10-10 |
| D-009 | **Detail fields come from a deployment profile in the codebase**: they cannot be changed from inside the app, and developers can set up variants of the tool with other field selections. Hence values are stored generically and validated against the profile, not as table columns (a different selection needs no migration). | Confirmed, 2026-10-10 |
| D-010 | Extras in scope: **CSV/Excel export** (D-033) and **API tokens for agents**. Not in scope: spreadsheet import, the backup command and page. | Confirmed, 2026-10-10 |
| D-011 | **Everything that can be tested is tested**; every milestone has an acceptance gate of automated tests, and requirements are traced to tests. | Confirmed, 2026-10-10 |
| D-012 | **Person = user**: one record per person, who may or may not be able to sign in (a password, an SSO identity, or neither yet). This differs from TaskBoard (person ≠ user) and simplifies the port. The built-in `admin` and `anonymous` are system accounts, not people: no timesheet, not in pickers or planning. | Confirmed, 2026-10-10 |
| D-013 | **Login required by default**: anonymous visitors hold nothing; signed-in users get *Viewer* globally and *Hours viewer* on their own department. Both are default grants an administrator can change. | Confirmed, 2026-10-10 |
| D-014 | A project's **coordinator** may view, edit and comment on it, and its **members** may view and comment, whatever their assignments. The built-in role **Project administrator** may edit all projects (and manage action plans) of the branch it is assigned on: one department, or all departments when assigned globally. | Confirmed, 2026-10-10 |
| D-015 | **Remarks are TaskBoard's conversation**: Markdown rendered and sanitized on the server, images attached by button, paste or drop (PNG, JPEG, GIF, WebP up to 10 MB, recognised by their bytes), Write / Preview, a toolbar, edit history, images in a lightbox, `@name` highlighted; plus the design's one level of replies and its "Done / Next steps" template (TaskBoard D-046 – D-049, D-085, D-099). | Confirmed, 2026-10-10 |
| D-016 | The **logbook records the core project fields**: creation, title, status, start and end date, coordinator, people, action plans, goal, priority, org node. Detail fields are **not logged for now**; entries are generic (field, from, to), so logging them later is a small change. Tasks and planned days are not logged. | Confirmed, 2026-10-10 |
| D-017 | **Project numbers** are assigned by the server (highest + 1, or the profile's first number), never change, and are the permalink `/projects/{number}`. The ERP order is a separate detail field. | Confirmed, 2026-10-10 |
| D-018 | **Status changes are free** (any status to any other). Projects are deleted only with `project.delete` (administrators) and only when no hours are booked on them. **Stopped projects are hidden from the project list by default** (the profile's `hidden_statuses`); their status chip shows them. | Confirmed, 2026-10-10 |
| D-019 | A person's working time is a **work pattern** (hours per weekday, default 8 × 5); capacity factor = weekly hours / 40. There is no holiday calendar: **time off is booked on the timesheet** under *Time off* categories (default Vacation, Out of office). Time off fills the day like work, but is not spent time: it lowers the time available in People planning. | Confirmed, 2026-10-10 |
| D-020 | **Availability for planning** is days per year: by default the profile's 220 days × the capacity factor, **overridable per person and year** by administrators (`org.manage`). A quarter's capacity is the year's availability spread over the year's workdays. | Confirmed, 2026-10-10 (220 days, adjustable); Assumed (per person and year, by administrators) |
| D-021 | **Weekly planned hours** come from quarterly planned days, pro rata over the person's working days; they are kept exact and shown in whole hours. Other work is planned at 10 % of the weekly hours (profile). | Confirmed, 2026-10-10 |
| D-022 | Timesheet: time is booked per person, day, project (or category) and task (or *General*); **own hours only**; the current and past weeks only. The app books in steps of 1 h with a day cap of 10 h (profile), while the database stores minutes (D-038). | Confirmed, 2026-10-10 |
| D-023 | Timesheet lines: projects with planned hours that week, projects with booked hours that week, Other work, Time off; **"+ Add project"** offers any visible project In preparation or In progress, counted as unplanned. | Confirmed, 2026-10-10 |
| D-024 | **Phone support is minimal at first**: the timesheet works at phone width (cards in one column, + and − usable) and nothing else needs to. The design's dedicated phone variant comes later; the timesheet's state and rules live in layout-free modules so that it can be added without rework. The prototype's Desktop / Phone switch is a preview control and is not built. | Confirmed, 2026-10-10 |
| D-025 | The **celebration can be switched off per browser** in Appearance; with reduced motion only the modal shows. | Confirmed, 2026-10-10 |
| D-026 | Appearance **follows the OS mode** until chosen, remembered per browser (TaskBoard D-039); the two styles are **Playful** (default) and **Boring** (the design's *Managerial*), which uses font weights about 100 lighter. | Confirmed, 2026-10-10 |
| D-027 | **"Today" is the server's date**; `MOMATO_TODAY` pins it. `seed --sample` shifts the sample's dates so its 8 Oct 2026 becomes the seeding day; tests pin 8 Oct 2026 (TaskBoard D-086). | Confirmed, 2026-10-10 |
| D-028 | **Built for thousands of projects and hundreds of people**: no screen loads all projects. The project list is filtered, counted and paged on the server (50 rows per page, keyset paging by number, more rows loaded while scrolling, with a "Load more" button as fallback); search and pickers ask the server; the bootstrap carries the org tree, people and plans, never projects; People planning loads a person's project lines when the row is expanded. | Confirmed, 2026-10-10 (the scale); Assumed (the mechanism) |
| D-029 | **Timeline windows** on Projects and Action plans run from 1 January of last year to 31 December of next year; they may become adjustable later. | Confirmed, 2026-10-10 |
| D-030 | People planning **leaves out the Spent/Compare rows of people whose hours the viewer may not see**, with a count; drill-downs sum invisible projects into "Other projects"; totals include everything. | Confirmed, 2026-10-10 |
| D-031 | Action plans **leave out projects the viewer can't see** (rows, totals, feed). Linking a project to a plan needs `project.edit` on the project or `plan.manage` on the plan. | Confirmed, 2026-10-10 |
| D-032 | Gantt tasks are **edited in a dialog** (no dragging bars), reordered with buttons; deleting a task moves its booked hours to *General*. | Confirmed, 2026-10-10 |
| D-033 | **Exports are a proof of concept**: the project list as shown and the time entries of a period, each as CSV (UTF-8 with BOM, comma, ISO dates, decimal point) and XLSX (XlsxWriter), filtered by the same rights as the screens. More exports later. | Confirmed, 2026-10-10 |
| D-034 | Detail values are stored as **JSON text per project and field key**; values of fields dropped from the profile are kept but hidden. | Confirmed, 2026-10-10 |
| D-035 | The design's fonts are **open-source (SIL Open Font License: free to use and ship, no licence fee)** and are shipped inside the app instead of loaded from Google Fonts; its four nav icons are kept as inline SVG (no icon library). | Confirmed, 2026-10-10 |
| D-036 | **English UI**, en-GB date formats, ISO weeks starting on Monday. | Confirmed, 2026-10-10 |
| D-037 | **Sample data that looks well used**: TaskBoard's organisation and people (STL › Quality, Process, Maintenance; R&D › Coatings; Anna Claes, Bram Peeters, Chloé Martens, Dries Wouters, Eva Janssens, Filip Maes), extended to about 10 departments, 70 people, 200 projects and 12 action plans with two years of booked hours. Anna Claes is "me" and has the design's week 41. Every sample person can sign in when seeded with `seed --sample --demo-password …` (TaskBoard D-023). Performance tests use a separate, larger scale data set. | Confirmed, 2026-10-10 |
| D-038 | **Time is stored in whole minutes** (integers): exact, portable, and ready for sub-hour booking later by changing the profile's step; hours and days are derived for display. | Confirmed, 2026-10-10 |
| D-039 | **"Last full week / month" in Spent and Compare means before the current ISO week / month**: on a Saturday the past week is still the week before the current one, and "Past year" ends with last month. Buckets: five days of the last ISO week, the last four ISO weeks (Monday to Friday), the last twelve calendar months. | Assumed, 2026-10-10 (M1; the requirement says "ended before today") |
| D-040 | **Rules compute with exact fractions**: days and ratios are `Fraction` in the domain, stored as `Numeric(6,2)`; time is integer minutes. Weekly planned hours, quarter availability and expected progress are therefore exact, and class boundaries (40 %, 85 %, 102 %, ±15 %) never wander by a rounding step. Display rounds half up. | Assumed, 2026-10-10 (M1) |
| D-041 | **Planned days exist only for members, enforced by the database** (composite foreign key from planned days to the project's members); removing a member removes their planned days first (PD-4). Time entries have no such link, so non-member bookings stay possible (PD-5). | Assumed, 2026-10-10 (M1) |
| D-042 | **The sample data is built relative to today**: the design's 16 projects keep their numbers and dates (shifted by the number of days between the sample's 8 Oct 2026 and the seeding day), the rest is generated from a fixed seed; time is booked on working days up to yesterday. Anna Claes takes the design's role of Anouk Smit (timesheet "me"); the root is named "Brightwater Industries" as in the design. | Assumed, 2026-10-10 (M1) |
| D-043 | **Default grants are data, created once**: the signed-in and anonymous defaults (D-013) are rows an administrator can remove or change; a marker (`app_state`) keeps them from being recreated at the next start. The anonymous visitor's grants are the default grants of the anonymous audience, not role assignments of the `anonymous` account. | Assumed, 2026-10-10 (M2) |
| D-044 | **The lockout guard counts active accounts holding `users.manage` globally by a role assignment** (not through default grants, and not the `anonymous` account): any change that would leave none is refused. | Assumed, 2026-10-10 (M2) |
| D-045 | **Edits of scalar core fields and details carry the project's version (409 when stale); members and plan links are set operations without one** (adding twice or removing a missing one changes nothing, and two editors adding different people never conflict). Tasks carry their own version; a planned-days cell is last write wins. | Assumed, 2026-10-10 (M3) |
| D-046 | **The bootstrap and every data endpoint answer 401 to a visitor who may see nothing, and 403 `password_change_required` to a person who must change their password**; lists are otherwise filtered, never refused. | Assumed, 2026-10-10 (M3) |
| D-047 | **Search and the project list differ on hidden statuses**: the list leaves Stopped out unless its chip is selected (PL-2), the pickers (project search, "+ Add project") find any visible project. | Assumed, 2026-10-10 (M3) |
| D-048 | **Where the design misses WCAG 2.1 AA (APP-4) the token is adjusted, not the rule**: muted and faint text use the design's l500 step (it has l520 and l600), the count on a selected status chip is no longer dimmed, and text on the accent is dark in dark mode (the accent is light there), as the design's "text on ink/accent" row says; the gantt's "Today" pill uses the darker accent step (l550) for its small white text, and the timesheet's "+1 h" pill and ✓ badge use the l500 step of the line colour (the design's l680 is too light for white text). The test suite runs axe on every screen in all four appearances, so a new miss fails the build and gets its own adjustment here. | Assumed, 2026-10-10 (M4) |
| D-049 | **Narrow screens (below 720 px) show both panes as rails whatever was remembered; a rail opens its pane over the page** (closed again by choosing, Escape or the backdrop). The remembered collapse states apply to wide screens only, and widening the window shows them again. | Assumed, 2026-10-10 (M4) |
| D-050 | **Remarks on the API are `remarks` (replies included, `/api/remarks/{id}`); the tab's count and `remark_count` are the live remarks**, so a "Remark deleted" placeholder kept for its replies is not counted. A deleted remark's author and text are not sent. Replies are text only (the server refuses image references in them). The Markdown preview is open to any signed-in person: it exposes nothing. | Assumed, 2026-10-10 (M5) |
| D-051 | **A project page's URL carries the filters of the list it was opened from** (`?node=&status=&q=&name=&coordinator=`), so "← Projects" returns to that list and ‹ › step through it; a project that is not in that list steps through all visible projects instead. | Assumed, 2026-10-10 (M5) |
| D-052 | **Timesheet cells are addressed by a line key and a task key** (`project:4102` + `task:12` or `general`; `other_work` / `time_off` + a profile category) and a write sets the cell's absolute minutes; zero removes the row. Days still to come in the current week can be booked (D-022); a week that has not started is refused, also for reading (422). A booking that would pass the day cap is refused unless it lowers the cell. | Assumed, 2026-10-10 (M7) |
| D-053 | **"+ Add project" lines live in the browser until time is booked**: the server lists only planned projects and projects with time that week, so an unplanned line disappears on reload when its time is gone (TS-8). The week card in the bootstrap and the timesheet come from the same service code, and the open timesheet keeps the sidebar's card current as the person books. | Assumed, 2026-10-10 (M7) |
| D-054 | **Saves still waiting when the page closes are sent with `keepalive` requests** (`pagehide`), so a reload right after quick clicks keeps the total. | Assumed, 2026-10-10 (M7) |
| D-055 | **People planning rows are the active people of the branch; the person filter runs on the server** (`q`), and a person's lines are loaded when the row is opened and again when mode or period change while it stays open. Spent and Compare leave out people whose hours the caller may not see and say how many; Planned shows everyone. A project the caller cannot see is summed into "Other projects" and always counts in the totals (PPL-7). Compare's planned days are the person's planned days (members only, D-041), so a booking on a project they are not a member of is a red "not a member" line. | Assumed, 2026-10-10 (M8) |
| D-056 | **Action plans: the plan page keeps its state in the URL and manages from a menu**: choosing a project puts the plan and the project in the URL (`/plans/12?project=4102`); changing branch drops the project (a selection belongs to the plan it was made in), and the feed follows the project shown in the summary. A plan's owner and manager edit or delete it from a "⋯" menu next to its name (AP-3). "+ Add project" and "Remove from plan" are offered to people with `plan.manage` in the plan's branch or `project.edit` anywhere; the server decides per project (D-031), so a coordinator's implicit right is used from the project's own "+ Action plan". The owner picker of a new plan lists the branches the person's `plan.manage` reaches. | Assumed, 2026-10-10 (M9) |
| D-057 | **Only deactivation takes a person out of the work.** A suspended sign-in (users.manage) ends their sessions and refuses new ones, but they stay in pickers, planning rows and as coordinators or members; a deactivated person (org.manage) is out of pickers and planning but keeps all history and can be reactivated. The bootstrap's `active` means "not deactivated". | Assumed, 2026-10-10 (M10) |
| D-058 | **Administration is `/api/admin`, split by right**: `org.manage` for the org tree, a person's data, availability and deactivation; `users.manage` for sign-in, passwords, suspension, assignments, roles, default grants and the audit log. The people list needs either and carries sign-in and rights fields only for `users.manage` holders. A password set by an administrator is generated by the server (shown once) or chosen, must be changed at the first sign-in, and ends the person's sessions. Org tree changes return the whole tree; sibling names are unique; a branch is deleted only when nothing refers to it. | Assumed, 2026-10-10 (M10) |
| D-059 | **API tokens act as their owner, narrowed by scope, and decide alone.** `mm_…` secrets are shown once and only their SHA-256 is stored; a *read* token holds the view permissions and is refused (403) on every request that is not GET, HEAD or OPTIONS; a *write* token holds everything but `org.manage` and `users.manage`. A scope narrows the owner's implicit coordinator and member rights too (a read token of a coordinator cannot edit). A request with a Bearer header is judged by that token alone: a bad, revoked or expired token, or an owner who is suspended or deactivated, is 401, never the cookie's person or a visitor, and it needs no CSRF header. Tokens are created and revoked in MoMaTo itself, never through a token (also no password change); at most 25 live tokens per account; people with `users.manage` can list and revoke anyone's. What a token writes keeps its token id on logbook entries, remarks (and their versions) and time entries, shown as "via <name>"; revoked tokens stay so the name stays. | Assumed, 2026-10-11 (M11; TaskBoard D-097) |
| D-060 | **Exports are plain GET downloads, written completely before they are sent.** `GET /api/exports/projects` (the list's filters; core fields then every profile detail field) and `GET /api/exports/time-entries` (`start`, `end`, optional `node`; at most three years; only people whose hours the caller may see). CSV starts with a byte order mark, uses commas, ISO dates and a decimal point, and "yes"/"no" for booleans; XLSX has one sheet with typed cells and a frozen bold header. The file is built in batches into a spooled temporary file and streamed from there, so memory stays flat and the database session is finished first. | Assumed, 2026-10-11 (M11; D-033) |
| D-061 | **Single sign-on is a port of TaskBoard's, with people instead of accounts.** An external identity is matched to a person already linked, else a prepared person by email, else by login name, else rejected or created without rights (`MOMATO_SSO_UNKNOWN_USERS`); system accounts are never linked; suspended and deactivated people are refused. Groups a provider reports are kept with the link and mapped to roles by administrators (`group_role_mappings`, same scopes as assignments), so they add to a person's own rights. Redirect sign-in uses single-use state, nonce and PKCE; Windows sign-in is one endpoint that starts an ordinary session, tried by the page once per tab; the trusted header is believed only from trusted proxies. `MOMATO_PUBLIC_URL` names the address people type (SSO callbacks, agent guide). | Assumed, 2026-10-11 (M12; TaskBoard D-063 – D-070) |
| D-062 | **Scale and appearance are measured by opt-in suites, and MS SQL is documented rather than run.** `-m scale` generates 5,000 projects, 500 people and about 750,000 time entries (`tests/scale.py`, deterministic) and asserts the budgets of REQUIREMENTS §8.5 in-process and in the browser; `-m visual` compares one screenshot per screen and appearance with the baselines in `tests/e2e/baselines` (a pixel counts as different above 12/255 per channel, at most 0.2 % may differ; updated deliberately with `MOMATO_UPDATE_VISUAL=1`). Both stay out of the default gate because they take minutes and the baselines depend on the browser build. The MS SQL run needs a SQL Server database; the suites already accept `MOMATO_TEST_DATABASE_URL` and `docs/OPERATIONS.md` says how to run them. | Assumed, 2026-10-11 (M13) |
